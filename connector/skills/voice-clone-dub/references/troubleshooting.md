# 故障排查

## 症状 → 原因 速查

| 症状 | 先查 | 处理 |
|---|---|---|
| 质检 `cov` 0.8 左右、`head` 低于 0.5 | 语速 | 见下面「吞句首」 |
| 参考段听起来有伴奏残留 | 分离 | 换更干净的源片；或手工截一段纯人声替换 `ref.wav` |
| 音色不像原片 | 参考段长度/内容 | `ref.wav` 要 10–13 秒连续说话，避开音乐段落 |
| 韵律发飘、断句奇怪 | `ref.txt` | 逐字校对参考文本 |
| 数字念成英文/念糊 | 归一化 | 确认 `tts_normalize.py` 被调用（`clone-tts.py` 默认开） |
| `Could not load libtorchcodec_core4.dll` | torchaudio | 已内置 monkeypatch 用 soundfile，若仍报错查 torch 版本 |
| `ImportError: cannot import name 'F5Tts'` | 类名 | 新版是大写 `F5TTS` |
| 下载只得到 70KB 的 JS | 反爬 | 必须走无头 Chrome CDP，不能用 curl |
| `Fresh cookies needed` | yt-dlp | 别用 yt-dlp 抓抖音，走 `dl-link.mjs` |
| ffmpeg 打不开 concat 输入 | 路径 | concat 列表里写**绝对路径** |
| whisper 校验少了上百字 | VAD | `vad_filter=True`，否则会整段吞 |

## 吞句首（最常见的质量问题）

**表现**：整段听起来没问题，但开头少了几个字，像「一句话从半截开始」。
总覆盖率可能还有 0.96，只有单独看 `head` 才暴露。

**根因**：`tts.infer(speed=N)` 不是后处理变速，而是**按比例压缩目标时长**。
`speed=1.2` 意味着模型要用 1/1.2 的时间念同样多的字，塞不下就会丢开头。

**实测**（同一段 43 字文案，同一个音色，nfe=16）：

| speed | 时长 | cov | head | 转写开头 |
|---|---|---|---|---|
| 1.2 | 5.24s | 0.842 | 0.50 | 「机一天能处理…」（丢「这台智能分选」） |
| 1.0 | 6.29s | 1.000 | 1.00 | 「上这台智能分选机一天能处理…」 |

三次重渲 md5 各不相同（采样确实随机），但每次都吞同一句 —— 说明是系统性挤压，不是运气。

**处理**：生成一律用 `speed=1.0`，要变速用 ffmpeg：

```bash
ffmpeg -y -i raw.wav -filter:a atempo=1.2 -ar 44100 -ac 1 out.wav
```

`atempo` 保音高（WSOLA），1.2× 几乎无损；范围 0.5–2.0，超出要串联。
`dub.mjs` 已内置这个逻辑，`--speed` 只会影响 atempo，不影响模型。

## 参考文本错了会怎样

参考文本参与「参考音频 ↔ 文本」的对齐。错字会让模型把音素边界学歪，结果是：
音色还在，但语流黏连、重音错位、停顿怪。

ASR 在这个场景的错误率不低（「获得萤石精矿」→「破除石英、金钨」，
「密闭煅烧」→「密地断烧」）。**建完档案务必先听一遍 `ref.wav`、对着改 `ref.txt`**，
改完把 `meta.json` 的 `refTextVerified` 置 true。

## 重渲还是不过怎么办

1. `--nfe 32`（两倍耗时，质量略好）
2. 把那段文案手工改短（拆成两句），或删掉拗口的成分
3. `QC_MIN=0.9 QC_HEAD=0.8` 放宽阈值，先交付再人工听
4. 换参考段：手工从原片截 10 秒纯人声覆盖 `ref.wav`，然后删掉 `ref.txt` 重新转写

## 性能参考（CPU，无独显）

- 43 字 / 1 段：约 70 秒合成 + 20 秒质检
- 274 字 / 5 段：约 12 分钟，含重渲可能 19 分钟
- 实时率 0.045–0.09×，波动来自句子长度与 CPU 负载

要快只能换引擎（如 edge-tts 预设音色，10 秒），代价是声音不是原声。
